## 🃏 Cards

### 🧱 Architecture — 4/5

The tag graph is real, not drawn. Every project's `nx.tags` matches
[`boundaries.ts`](../../packages/configs/src/eslint/lib/boundaries.ts) and the
[root README's table](../../README.md#-architecture--boundaries) verbatim — including the
`type:tooling` row for `@monorepo/scripts`, which is not even committed yet — and the rule is
registered as `"error"`, not warn. `content` and `i18n` each cut a genuine port/adapter seam:
`core/domain` imports nothing, the vendor lives behind `ContentProvider`/`TranslationProvider`, and
`registry.ts` dynamically imports the vendor module by name, so adding one is a map entry rather
than a change to any caller. `apps/external` composes leaves through their published `exports`
entry points only, never a deep path into another package's `src/`, and the single `process.env`
read in the tree sits in the one project that is an actual HTTP service. What keeps it off a 5 is
that the invariant the whole seam rests on — `core/` never importing `@nuxt/kit`, `h3` or
`nitropack` — is enforced by nobody. `@nx/enforce-module-boundaries` reasons about project-to-project
tags, not subpaths inside one project, and those peers are already in `devDependencies`, so a stray
import would compile and pass CI clean.

| The `core/` → Nuxt import ban is prose with no enforcement path | [`packages/content/CLAUDE.md`](../../packages/content/CLAUDE.md) and [`packages/i18n/CLAUDE.md`](../../packages/i18n/CLAUDE.md) state it; [`boundaries.ts:1-73`](../../packages/configs/src/eslint/lib/boundaries.ts) is tag-level only, and no `no-restricted-imports` rule exists in `packages/configs/src/eslint/lib/` |

`OfetchHttpClient` in each package diverges only where the port itself does.

### 🧩 Implementation — 4/5

Zero `any`, zero `@ts-ignore`/`@ts-expect-error`, zero `eslint-disable` across 88 source files, and
that one is enforced rather than merely observed: `no-explicit-any` is an error through the
`recommendedTypeChecked` set pulled in by
[`packages/configs/src/eslint/node.ts:12`](../../packages/configs/src/eslint/node.ts), and that lint
run is both the [pre-push hook](../../.husky/pre-push) and CI. Error paths are honest everywhere.
Both `OfetchHttpClient`s rethrow as a typed `UpstreamError`; the BFF routes pass a domain error
through untouched and re-wrap only a genuinely unknown cause; the translations controller separates
a missing file (404) from a read or parse failure (500) instead of collapsing both. Malformed vendor
payloads are handled explicitly rather than trusted — WordPress's `x-wp-total` is guarded against a
proxy dropping it, and Tolgee's response is checked for the requested locale before use. `content`
and `i18n` look alike where they should and differ only where the domains do, with each divergence
argued in the packages' `CLAUDE.md` rather than left as drift.

| Costs a point | Evidence |
| --- | --- |
| A byte-identical `toWordChars` lives in two packages that cannot share code, with nothing pinning them together | [`packages/content/src/core/contentKey.ts:9-11`](../../packages/content/src/core/contentKey.ts#L9-L11) vs [`packages/i18n/src/core/translationsKey.ts:15-17`](../../packages/i18n/src/core/translationsKey.ts#L15-L17) — the boundary forces the copy, but fixing one silently leaves two cache-key schemes, and the tradeoff isn't written down |

### ⚙️ Tooling & DX — 3/5

bump really does invalidate every project, `build` and `test:coverage` declare outputs that match
what Nuxt, Storybook and Vitest actually write, and style is settled by a `PostToolUse` hook rather
than argued in review. The pre-push/CI gap — CI also runs `build` — is written down in two places,
which is exactly what keeps it from costing anything. Two other gaps do cost. `lint` and `typecheck`

tells a human to run the full `run-many`, which nothing enforces. Separately, husky cannot install
itself here (lifecycle scripts are banned), and the one command that fixes a fresh clone lives only
in `CLAUDE.md`.

regex and rejects any pushed `TODO`/`FIXME` while pointing at `pnpm issue:add` — and the tree holds

`CHANGELOG.md` files carry generated section headers and dependency cascades, and versions like
`0.0.8` and `0.1.3` are consistent with derivation rather than typing. The issue trail is live —
`feature/36-project-management` maps to open issue #36, so the current work is filed, not stranded
in a branch name.
